# Build Switchboard on two local processes

Build SWDB as two Node.js 26 processes that one `pnpm dev` starts: a TanStack Start app (dashboard, server functions, webhook and API routes, SSE) and a small worker (agent runs, cron ticker, MCP child processes, Slack and Discord connections). Both open **one SQLite file in WAL mode**, and the tool needs no container. TanStack covers routing, data, tables, forms and the web server. It cannot do two jobs today: Start documents nothing for background work, and TanStack Workflow is at 0.0.5 with no SQLite store, so the run engine is a hand-built loop that writes every model response and tool result to an append-only `run_events` table before acting on it. That one log is the crash-recovery checkpoint, the live stream to the browser and the trace view. The harness is a hand-written loop on OpenRouter's Chat Completions endpoint, with the model as a string per request and cost read from `usage.cost` on every response. Questions and approvals go through one `human_requests` table that the dashboard inbox, Slack, Discord, email and SMS all resolve through the same compare-and-set function. Track the work in GitHub Issues and Projects. **No hands-on test was run during this research.** Version numbers come from the npm registry on 2026-11-19, the architecture is inference from cited designs, and several items rest on secondary sources. Eight short spikes, listed below, settle the open risks before the bulk of the build.

## Recommended stack: TanStack Start, one worker, one SQLite file

The scope decides most of the stack. SWDB is a private single-user tool on one Mac, so every option that adds a service is weighed against a design that runs with `pnpm dev` and nothing else. The second constraint is the stated preference for TanStack Start and the TanStack family. TanStack Start 1.0 was announced stable on 2026-10-13, with typed server functions, server routes that take a standard `Request` and return a `Response`, and middleware. Its announcement and docs do not mention background jobs, WebSockets or long-running processes ([TanStack Start 1.0 blog](https://tanstack.com/blog/tanstack-start-1-0), [server routes guide](https://tanstack.com/start/latest/docs/framework/react/guide/server-routes)). A community answer recommends "a separate worker or server for the background task" ([Answer Overflow thread](https://www.answeroverflow.com/m/1317249301507866746)). That is why the design has a second process. Agent runs that last minutes, the queue consumer, the schedule ticker and MCP stdio child processes belong in the worker, because in development Start's server code runs inside Vite's dev server, where a module reload would restart a ticker and orphan child processes. That last point is inferred, not sourced.

## Harness and system architecture: one event log does three jobs

### Processes and repository layout

The repository is a pnpm workspace with `apps/web` (TanStack Start), `apps/worker`, `packages/db` (schema and migrations) and `packages/core` (harness, run loop, event types). Internal packages export `.ts` sources directly because both Vite and Node 26 consume TypeScript. The web process writes triggers, enqueues runs, serves the dashboard and SSE, and receives webhooks. The worker claims runs, appends events, runs the schedule ticker, holds MCP stdio child processes, and keeps the Slack Socket Mode and Discord gateway connections open. Both are outbound WebSockets, so they work with no public URL ([Slack Socket Mode docs](https://docs.slack.dev/apis/events-api/using-socket-mode), [Discord docs](https://docs.discord.com/developers/interactions/receiving-and-responding)). With two processes, the SSE route follows new events by polling the table every 250 to 500 ms. A login item or `launchd` agent that starts SWDB at login makes cron fires and artifact links dependable.

### Run engine and event log

An agent run is a loop of model calls and tool calls. The harness appends each model response and each tool result to `run_events` before it acts on it, so after a crash the worker reloads the log and continues from the last completed call. Anthropic's Managed Agents post describes the same split: an append-only session log outside the harness, and a harness that holds no state that must survive a crash ([Anthropic: Managed Agents](https://www.anthropic.com/engineering/managed-agents)). The resume rule comes from an OpenCode failure report in which tool parts stayed `running` after a restart: any tool call with no recorded result gets a synthetic "interrupted" tool result, so the transcript stays valid for the provider ([opencode issue #19023](https://gh.ali360.cloudns.ch/anomalyco/opencode/issues/19023), a GitHub mirror, not official docs).

The event types follow pi-agent-core and the Claude Agent SDK, which both use a run, turn and message-or-tool hierarchy ([pi-agent-core](https://www.npmjs.com/package/@earendil-works/pi-agent-core), [Claude Agent SDK: agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)): `run_start`, `turn_start`, `model_request`, `model_response`, `tool_start`, `tool_end`, `approval_requested`, `approval_resolved`, `child_run_started`, `child_run_ended`, `compaction`, `retry`, `limit_hit`, `error`, `run_end`. Token deltas are stream-only or batched into one row every 50 to 100 ms. No source quantified SQLite write throughput for per-token rows. Every run ends with exactly one terminal event that carries cost, usage, turn count and a reason code from a fixed set (`success`, `max_turns`, `max_budget`, `timeout`, `cancelled`, `error`), on failures too. The same log drives the browser: `GET /runs/:id/events` selects `seq > Last-Event-ID`, streams the backlog, then follows. TanStack AI's resumable-streams design and Cloudflare's agents runtime both use one append-only log per run with the sequence number as the cursor ([TanStack AI resumable streams](https://tanstack.com/ai/latest/docs/resumable-streams/overview), [Cloudflare Agents streams](https://developers.cloudflare.com/agents/runtime/capabilities/streams/)).

### The loop on OpenRouter

OpenRouter returns `usage.cost` in every response, lists `supported_parameters` per model, and accepts a different model string on every request, so per-agent model choice costs nothing in the harness ([OpenRouter API overview](https://openrouter.ai/docs/api-reference/overview)). On 2026-11-19 the models API listed 479 models, 416 with `tools` and only 18 with a controllable `parallel_tool_calls` ([OpenRouter models API](https://openrouter.ai/api/v1/models)). The agent editor should therefore offer only models whose `supported_parameters` include `tools` and `tool_choice`, and the loop must tolerate one or several tool calls per turn.

The loop has six duties beyond "call, run tools, repeat". It passes `reasoning_details` back unmodified and in order ([reasoning tokens](https://openrouter.ai/docs/use-cases/reasoning-tokens)). It handles a 429 that arrives mid-stream as an SSE event with `finish_reason: "error"`, and reads `limit_source` on 402 and 403 responses ([limits](https://openrouter.ai/docs/api-reference/limits)). It validates tool calls against OpenRouter's four published failure buckets (invalid JSON, unknown name, missing name, schema mismatch) and returns an error tool result so the model can retry, with a cap on repair rounds ([Auto Exacto](https://openrouter.ai/docs/guides/routing/auto-exacto.md)). It sums `usage.cost` after each call and stops before the next call when the sum passes the run budget; the Claude Agent SDK docs note that such a check overshoots by up to one response. It runs read-only tools concurrently and mutating tools in sequence, and stores results in the assistant's call order. It sends a stable `session_id` per run, which starts provider sticky routing for prompt-cache hits ([prompt caching](https://openrouter.ai/docs/features/prompt-caching)). A per-agent OpenRouter key with a spend limit is the backstop under the in-process budget; creating such keys by API was not verified.

Which library sits under the loop is the one stack decision the notes leave open. They rank lock-in from lowest to highest: raw API, pi-agent-core, AI SDK v7, `@openrouter/agent` (beta), Mastra, VoltAgent and LangGraph, then the Claude Agent SDK (bound to Claude models). The recommendation is a hand-written loop on Chat Completions, because the requirement is an own harness and the loop's event schema is the product's data model. `@tanstack/ai` 1.7.0 with `@tanstack/ai-openrouter` 1.1.2 is the TanStack candidate, and its adapter reports `usage.cost` on the final `RUN_FINISHED` event ([TanStack AI OpenRouter adapter](https://tanstack.com/ai/latest/docs/adapters/openrouter.md)). Its iteration limits, approval API, cancellation, persistence hooks and MCP support were not on the pages read, so it needs the spike described below before it carries the loop. It fits the dashboard's "test this agent" chat panel either way. AI SDK v7 with `@openrouter/ai-sdk-provider` 3.1.0 is the fallback: it supplies stop conditions, four timeout scopes, tool approvals and an MCP client, and has no cost-budget stop condition in the pages read ([Vercel: AI SDK 7](https://vercel.com/blog/ai-sdk-7), [AI SDK loop control](https://ai-sdk.dev/docs/agents/loop-control)).

### MCP and skills registry

The global settings area holds MCP servers and skills once; each agent selects from them, and nothing is enabled by default. Cursor's docs note that connecting an MCP server grants every tool it exposes, and Claude's scheduled tasks include all connectors by default and advise removing them ([Cursor docs](https://cursor.com/docs/cloud-agent/automations), [Claude Code docs](https://code.claude.com/docs/en/routines.md)). SWDB selects per (server, tool).

The current MCP revision is 2026-07-28. It removes the `initialize` handshake and sessions, requires `ttlMs` and `cacheScope` on list results, and replaces server-initiated requests with a retry pattern in which a tool call returns `input_required` and the client retries with `inputResponses` ([2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). The client must still talk to older servers. The design consequences are inferences: one lazily started child process per stdio server with an idle timeout; a tool-list cache keyed by server, credential and protocol version; a hash of each tool's full definition stored at approval time, with the tool disabled for all agents when the hash changes until the user reviews a diff; tool names prefixed with the server slug and a reverse map; and the per-agent allowlist enforced twice, once when building the tool list for the model and again in the dispatcher. Import accepts pasted JSON with either `mcpServers` or `servers` as the root key and moves `env` and `headers` values into the secret store. The claim that VS Code uses `servers` comes from secondary sources. Stdio servers get pinned versions (`npx pkg@1.2.3`), and each child's environment is built from an explicit allowlist, never from the SWDB process environment. For OAuth, the spec requires persisted credentials to be keyed by issuer. A localhost-only app probably cannot host the Client ID Metadata Document that the spec now prefers, so local SWDB would depend on the deprecated Dynamic Client Registration or pre-registered client IDs; that is an inference to check against the spec.

Skills follow the Agent Skills format: a directory with `SKILL.md`, required `name` and `description` frontmatter, and optional `scripts/`, `references/` and `assets/` ([agentskills.io specification](https://agentskills.io/specification)). The implementer guide says what a harness does: put a name-and-description catalog in the prompt, activate through a file read or an `activate_skill` tool whose parameter is an enum of valid names, hide filtered skills from the catalog entirely, and exempt activated content from compaction ([agentskills.io implementer guide](https://agentskills.io/client-implementation/adding-skills-support)). SWDB installs a skill by fetching a git repository or tarball into its own skills directory, validates it, shows the full content and any scripts before enabling, stores a hash of the directory tree, and never auto-updates. The agent editor states when a skill contains scripts and therefore needs shell access. The experimental `allowed-tools` field is shown at install time and never granted automatically.

The reason for this caution is documented. Snyk's ToxicSkills audit scanned 3,984 skills from ClawHub and skills.sh as of 2026-02-05 and found 76 confirmed malicious payloads and 534 skills with a critical issue ([Snyk ToxicSkills](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub), vendor research). One late-October 2026 comparison found that static scanner rules blocked 7.7% of malicious skills at high severity ([particula.tech](https://particula.tech/blog/agent-skills-security-scanner-skillspector-cisco-snyk), a single secondary source). A scanner is a prompt for human review; capability restriction carries the weight.

### Permissions and sandbox levels

Claude Code's docs state that a Bash permission rule "isn't a security boundary around the program" and that argument-constraining patterns are fragile ([Claude Code permissions](https://code.claude.com/docs/en/permissions)). A command allowlist reduces prompts; enforcement comes from the sandbox. The notes derive three levels per agent.

| 3. Container                | Free-form shell inside a container or lightweight VM per run, repo cloned by the harness before the first model call                                                                                                                                                                          | Docker or OrbStack (OrbStack not researched), or Apple `container` 1.0 with one lightweight VM per container (secondary sources)                                                                                                                                             |

The rule model is three effects (allow, ask, deny) with deny evaluated first, and default deny for trigger-started agents. That matches Claude Code's `dontAsk` mode, where pre-approved tools run and anything that would prompt is denied. Unattended agents with a shell require level 2 or 3, and a sandbox failure fails the tool call with no unsandboxed retry.

For the code-review example, checkout is a harness step. The agent config or the webhook payload names the repository and ref, SWDB clones it into `<data>/workspaces/<agentId>/<runId>/`, and the model gets `exec` and file tools bound to that sandbox. The preferred credential design gives the sandbox no credential: the harness clones from outside, and the agent posts review comments through a GitHub tool on the host side. Claude Code on the web routes git through a proxy outside the sandbox that swaps a scoped credential for the real token ([Anthropic engineering: Claude Code sandboxing](https://anthropic.com/engineering/claude-code-sandboxing), read through a search summary). Managed Agents docs state the limit of host allowlists: "Network access is granted by host, not by operation", so an allowed host such as github.com can receive a push ([Cloud environment setup](https://platform.claude.com/docs/en/managed-agents/environments)). Read-only credentials are the control that matters. The model never chooses the image, mounts, network policy or credentials. A `SandboxProvider` interface (`create`, `exec`, `readFile`, `writeFile`, `destroy`, optional `snapshot`) keeps `srt` and containers interchangeable.

The editor also tags each tool, server and skill with three booleans (reads untrusted content, reads private data, can write or send externally) and warns when one agent holds all three. This applies Meta's Agents Rule of Two as Simon Willison describes it ([Willison, 2025-11-02](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). Trigger payloads reach the model wrapped as untrusted data, following Claude's `<routine-fire-payload>` block, which labels the text as untrusted and requires the saved prompt to opt in ([Claude Code docs](https://code.claude.com/docs/en/routines.md)).

### Triggers

A webhook trigger is one row with an unguessable path token (`/hooks/<token>`), an auth mode (none, shared header secret, configurable HMAC, or Standard Webhooks), an optional filter and a payload-to-prompt template. Intake reads the raw body, verifies the signature, computes a dedup key, inserts a `webhook_deliveries` row under a unique constraint, enqueues the run and returns 202. Standard Webhooks defines the headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) and HMAC-SHA256 over `msg_id.timestamp.payload` ([Standard Webhooks spec](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)). Stored deliveries give replay and an inspect view. The API trigger is `POST /api/v1/agents/:id/runs` with a hashed API key, plus get run, cancel run and list events. Cron lives in a `schedules` row with a cron expression, IANA time zone and persisted `next_run_at`. On each tick and at startup the worker selects due rows, applies `skip` or `run once` (pg-boss's two missed-run policies, [pg-boss scheduling docs](https://pgboss.io/api/scheduling)), and enqueues with an idempotency key of schedule ID plus scheduled time in the same transaction that advances `next_run_at`.

A tunnel that forwards the whole port exposes the dashboard to the internet. Forward only a second port or path prefix that serves `/hooks/*`, or put a local password on dashboard routes. The OpenClaw exposure reports are why local bind and auth stay in v1 for a single-user tool; the instance counts in those reports conflict between scanners and are secondary.

### Channels and the inbox

All channels implement one adapter interface with `send`, optional `sendApproval`, optional `start` for socket transports, and declared capabilities. Delivery has two paths. A deterministic post-run step, run by the harness, sends the final result or failure notice to the agent's attached channels, so a report arrives even when the model forgets to call a tool or the run crashes. A `notify` tool covers mid-run messages, with a schema of channel name (an enum of attached channels), title, body and urgency, and no recipient field. Recipients resolve server-side from `agent_channels`, because a model that can choose an address can be steered by injected text. Cursor restricts "Send to Slack" to one channel and gh-aw routes writes through declared safe outputs for the same reason.

The inbox is a fifth channel that is always attached. One `human_requests` table backs notices, free-text questions, approvals and choices. An `ask_human` tool and the harness's own tool-approval gate create the same row, set the run to `waiting_human`, and release the worker; nothing waits in memory. Every transport calls one function, `resolveHumanRequest(id, answer, via)`, which runs `UPDATE ... SET status='answered' WHERE id=? AND status='open'`. Only the caller whose update changed a row resumes the run, which is the "first answer wins" rule for the inbox UI, Slack button, Discord interaction, email link and SMS reply. The harness then edits the other copies. LangChain's Agent Inbox (accept, edit, respond, ignore) and Linear's `awaitingInput` session state are the closest published designs ([HumanInterruptConfig reference](https://reference.langchain.com/python/langgraph.prebuilt/prebuilt/interrupt/HumanInterruptConfig), [Linear agent interaction docs](https://linear.app/developers/agent-interaction)).

Three rules come from the references. Every request has `expires_at` and a default action, deny for approvals, because LangGraph, Trigger.dev and Managed Agents wait indefinitely by default and an unanswered item would hold a run open. The approval message shows the exact tool name and arguments, since approving a model-written summary is an injection path. On resume the harness re-executes nothing that ran before the pause and stores an execution marker on the request row. Approvals cannot run through an MCP tool that the agent itself calls, because the gate must sit outside the model's control. The dashboard holds one app-wide SSE connection that carries small invalidation events, and TanStack Query refetches on each. When no tab is open, the practical local answer is escalation to Slack or Discord, not web push.

### Artifacts

Agents write through a `save_artifact` tool that takes a filename, media type and content, never a path. The tool sanitises the filename and rejects path separators. Files land in `<data dir>/artifacts/<run_id>/<artifact_id>/<filename>` with a metadata row. The Managed Agents precedent is a designated outputs directory whose files are listed per session ([Adding files](https://platform.claude.com/docs/en/managed-agents/files)). No comparable product documents versioning of a recurring report, so a stable artifact key per agent with a new version per run, a "latest" link and a diff is SWDB's own addition.

Rendering treats agent output as untrusted. Markdown goes through react-markdown or streamdown with `rehype-sanitize` and without `rehype-raw`; remote images are blocked or proxied because an image URL can carry data out. HTML is never injected into the app DOM: it is served from a dedicated route with `Content-Security-Policy: sandbox` or loaded in an `<iframe sandbox>` without `allow-same-origin`, and a second localhost port gives the separate-site boundary one write-up argues for ([HackerNoon](https://hackernoon.com/three-security-boundaries-for-hosting-untrusted-ai-generated-html)). SVG is treated as HTML. CSV renders through papaparse into TanStack Table.

The Slack or Discord ping links to `<base URL>/artifacts/<artifact_id>` with a random ID. With base URL `http://localhost:<fixed port>`, the link opens on the same Mac. It does not open on a phone, and Slack and Discord cannot build a preview, because their servers cannot reach localhost. Reading on a phone needs the tailnet hostname or the tunnel hostname, and on a public hostname the artifact route needs a signed expiring token or the dashboard password. Including a short summary or the file itself in the message avoids the problem.

### Subagents and agent-to-agent communication

The dominant pattern is "subagent as a tool call": the parent calls one tool with a prompt string and an agent name, the child runs its own loop in a fresh context with its own tools and model, and only the child's final message returns ([Claude Agent SDK: subagents](https://code.claude.com/docs/en/agent-sdk/subagents.md)). In SWDB that is `spawn_agent({ agent, prompt, wait? })`, which creates a child run with `parent_run_id` and runs the same loop with the child's own definition. Managed Agents supplies the rule set to copy: the caller lists the registered agents it may call, delegation is one level deep, and the session budget covers child runs ([Multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)). The spawn tool enforces depth, concurrent children, per-child turn cap and a run-tree cost budget, and returns each refusal as a tool result. The parent treats the child's final message as untrusted input. A child cannot approve its own or a sibling's gated action, and inter-agent messages never satisfy an approval gate.

"Communicate with each other" has two readings. The synchronous one is the spawn tool. The asynchronous one reuses existing parts: agent A fires agent B's API trigger with a payload that B treats as untrusted data. A mailbox table and a shared task list with atomic claims exist as a documented design only in Claude Code's experimental agent teams ([Claude Code: agent teams](https://code.claude.com/docs/en/agent-teams.md)). The evidence for restraint is from mid-2025 and predates current models: Anthropic reported about 15 times the tokens of chat for multi-agent systems, and Cognition recommended a single-threaded agent as the default ([Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), [Cognition](https://cognition.com/blog/dont-build-multi-agents)). No 2026 controlled study was found. Persistent agents created by an agent (`create_agent`) are a later feature: no published guardrail guidance exists, and the notes' rules (new definitions are a subset of the creator's grants, start as drafts with no triggers, need human approval to enable) are inference.

### Logs and debugging

Process logs (server start, tunnel, scheduler ticks) go through pino. Run telemetry is rows: `run_events` with span columns makes a run a tree, `model_calls` stores the exact request body sent to OpenRouter and the full response, and `tool_calls` stores arguments, state, timing and a truncated result with a path to the full output. The dashboard reads those tables directly: a run list with status, cost and duration filters; a span tree per run with child runs nested; a transcript; a raw request and response inspector; and cost by agent, model and day. Two "replay" actions need separate buttons: read-only playback of the log, which is free, and re-execution of one model call from its stored request body, which costs money. Fork from step creates a new run with `forked_from_run_id` and `forked_from_seq`; tool side effects before the fork point are not undone, and the UI says so. "Succeeded" needs a stricter meaning than a clean exit, because Claude's own docs state that a Succeeded run can contain blocked requests and unfinished work visible only in the transcript.

The code will live on GitHub, and GitHub now has the pieces a feature tree needs: sub-issues and issue types reached GA in April 2025, issue fields reached GA on 2 July 2026, and the GitHub CLI exposes types, parent and sub-issue relationships and dependencies from the terminal since June 2026 ([GitHub changelog, April 2025](https://github.blog/changelog/2025-04-09-evolving-github-issues-and-projects/), [issue fields GA](https://github.blog/changelog/2026-07-02-issue-fields-are-now-generally-available), [CLI changelog](https://github.blog/changelog/2026-06-10-manage-sub-issues-types-and-dependencies-from-github-cli/)). A coding agent can therefore create the whole issue tree from the tables above with `gh`. GitHub is also where Copilot, Claude and Codex are assigned work through Agent HQ ([GitHub blog](https://github.blog/2026-02-04-pick-your-agent-use-claude-and-codex-on-agent-hq/)).

Linear's case is its agent delegation model, where assigning an issue to an agent triggers delegation, and its MCP server ([Linear docs](https://linear.app/docs/agents-in-linear.md)). Against it: it is a second system beside the code, one secondary source lists a 250-issue cap on the free tier, and sources conflict on which plans include Linear Agent. None of Linear's current plan limits were confirmed on linear.app. For one developer, those costs outweigh a delegation model that GitHub now approximates.

One caveat applies to GitHub. Issue fields are organisation-level, so a personal-account repository cannot use them, and issue types are organisation-level too according to prior knowledge that needs confirming in GitHub's docs. Create a free GitHub organisation for the repository. The structure the notes propose is their inference, since no authoritative recommendation for solo projects was found: issue types Epic, Feature, Task and Bug; one Epic per area (agents, triggers, runs, channels and inbox, registry, sandbox, artifacts, UI shell); sub-issues sized for one agent session; dependencies for ordering; milestones `v1-local`, `v1.1` and `later` mapped to the M, S and L rows; and an issue form with Context, Scope, Out of scope, Acceptance criteria as checkboxes, Test plan and Definition of done. Each coding-agent session starts without project memory, so every issue needs self-contained acceptance criteria and file pointers, with agent-specific detail in a collapsible section at the end. The eight spikes are the first issues, and M5, M6 and M16 depend on spikes 2, 3 and 4.

## Conclusion

The research changes the starting question. "Which framework" matters less than one table: `run_events` is at once the checkpoint that replaces a durable-execution engine, the SSE source that replaces a streaming service, and the trace store that replaces an observability backend. Every rejected alternative in the stack table is a service that would have owned one of those three jobs. The TanStack gap is also narrower than it first appears. It is a worker process and a run engine, and TanStack Workflow already has the same shape, so a later migration replaces the hand-built loop's persistence, not the design.

The feature list's weight sits where the comparables are weakest. Hosted products ship triggers and run history, but none combines per-agent model choice through OpenRouter, a local registry with nothing enabled by default, fixed-recipient outbound channels and a cross-agent inbox. The same evidence says the dangerous agent is the ordinary one: a webhook-triggered agent with an MCP server that reads private data and a Slack channel holds all three legs of the exfiltration pattern. The controls that address it (untrusted-payload wrapping, per-tool allowlists enforced at dispatch, recipients the model cannot choose, approvals outside the model's reach) are all in the must-have list. They cost little to build in at the start and are hard to add once agents are running unattended.
